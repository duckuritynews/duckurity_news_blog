보안 블로그 모바일 UI·UX 및 반응형 진단 요약
진단 기준일: 2026-10-03
대상: duckurity_news_blog의 로컬 작업 디렉터리
문서 성격: 앞서 수행한 진단 결과 정리. 이 문서 작성 시 검사를 다시 실행하지 않음.

1. 결론

현재 Astro 정적 사이트 구조를 유지하면서 모바일·PC의 재배치, 확대 대응,
검색과 페이지 이동 경험을 개선할 수 있다. 기본 반응형 구조는 폴드·플립의
화면 크기 변화에도 활용할 수 있다.

우선 개선 대상은 다음 두 가지다.
- 다크 모드 버튼의 글자와 배경 사이 명암 대비 부족.
- 검색 결과가 없을 때 '아직 게시된 기사가 없습니다'라는 잘못된 안내 표시.

브라우저 도구의 시작 오류 때문에 실제 화면 검사와 스크린샷을 수행하지 못했다.
실기기 접힘 전환, 화면 키보드, 확대, 스크린 리더 동작은 미검증이다.
코드로 개선할 수 있다는 판단은 실제 기기에서 해결을 확인했다는 뜻이 아니다.

진단 중 애플리케이션 소스·기사·설정·의존성을 수정하지 않았다.
추적 파일 34개의 변경 전후 해시가 같았고, 기존 크림 옐로 관련 CSS 변경도 보존했다.
커밋·푸시·배포는 수행하지 않았다.

3. 환경별 판정

D01. 검색 결과 없음 / 재현된 문제
근거: index.astro:40, search-client.js:79.
없는 CVE를 검색하면 '검색 결과가 없습니다'와 '아직 게시된 기사가 없습니다'가
함께 표시된다. 검색 일치 없음과 사이트에 기사가 없는 상태를 혼동시킨다.

D02. 다크 모드 버튼 / 코드상 위험
근거: global.css:43, tokens.css:45.
흰 글씨와 #A2EDDF 배경의 계산 대비는 약 1.34:1이다.
일반 크기 글씨의 4.5:1 기준에 미달한다. 실제 렌더링 상태는 미검증이다.

D03. 좁은 화면·폴드 외부 화면 / 코드상 위험
근거: global.css:27·63. 헤더와 페이지 이동 영역에 줄바꿈 규칙이 없다.
좁은 폭과 큰 글자가 결합하면 충돌할 가능성이 있다. 실제 넘침은 미확인이다.

D04. 펼친 화면·넓은 PC / 검사 범위에서 문제 없음
근거: tokens.css:12·13. 본문 최대 폭은 이미 제한되어 있다.
목록은 1열이며, 다열화가 반드시 필요하다는 근거는 없다. 시각 검사는 미검증이다.

D05. 분할 화면 / 검사 범위에서 문제 없음
유동 폭과 viewport 기준 미디어 쿼리를 사용한다. 기기 전체 해상도에 의존하지 않는다.
실제 작은 창에서의 배치는 별도 확인해야 한다.

D06. 회전·낮은 창 / 미검증
고정 헤더·하단바에 의한 가림 원인은 없다. 낮은 화면의 조작 편의는 미확인이다.

D07. 접고 펴기·읽기 연속성 / 미검증
resize에 의한 재생성은 없다. URL의 검색어·정렬·페이지 복원 검사는 통과했다.
실제 기기에서 포커스·스크롤·OS 재로드 이후 상태는 확인하지 못했다.

D08. 힌지·부분 접힘·플립 커버 / 미검증
실기기가 없다. 가림 여부와 커버 화면의 웹 실행 가능 여부부터 확인해야 한다.

D09. 주소창·도구 모음 변화 / 미검증
전체 화면 고정 UI는 없다. 현재 코드만으로 높이 잘림을 확정할 근거는 없다.

D10. 화면 키보드 / 미검증
검색창과 버튼은 일반 문서 흐름에 있다. 입력 중 접근성과 자동 스크롤은 미확인이다.

D11. 노치·시스템 영역 / 미검증
viewport-fit=cover와 safe-area 처리는 없다. 이 사실만으로 가림 결함은 아니다.

D12. 큰 글자·확대·텍스트 간격 / 코드상 위험
줄바꿈 없는 영역과 rem/vw 혼합 clamp가 있다. 확대 제한은 없다.
글자만 200% 확대했을 때 제목·버튼이 충분히 확대되고 재배치되는지 확인해야 한다.

D13. 터치·마우스·키보드 / 검사 범위에서 문제 없음
실제 링크·버튼·select, 초점 표시, 비활성 이동 방지가 구현되어 있다.

D14. 페이지 이동 후 읽기 위치 / 코드상 위험

다음 페이지에서도 화면 아래에 머물러 새 결과의 시작을 놓칠 가능성이 있다.

D15. 긴 URL·해시·파일 경로 / 코드상 위험
제목·요약·본문에는 overflow-wrap:anywhere가 있다.
저자·핵심 요약·출처 일부에는 없어 특정 긴 문자열에서 넘침 가능성이 있다.

D16. 표·코드 / 검사 범위에서 문제 없음
근거: global.css:76·78. 개별 가로 스크롤이 있고 생성된 코드에는 tabindex=0이 있다.
표의 키보드 스크롤과 보조 기술 읽기 순서는 미검증이다.

D17. 기술 이미지 / 미검증
생성 이미지 8개 모두 폭·높이가 지정되었고 비율을 유지한다.

D18. 느린 통신·많은 검색 결과 / 코드상 위험

기사 수 증가 시 처리·로딩 비용이 커질 수 있다. 실제 지연은 측정하지 않았다.

D19. 브라우저·앱 내부 브라우저 / 미검증
실행 도구 문제로 브라우저별 select·IME·뒤로가기·콘솔 오류를 검사하지 못했다.

D20. 메뉴·목차·모달·하단바 / 해당 없음
현재 없는 기능이다. 진단을 위해 새로 도입할 필요가 없다.

  힌지 대응 구조 변경이나 기사 강제 2열 배치의 근거가 없다.
- D04·D05·D20: 추가 변경 불필요.
  본문 최대 폭·viewport 기반 배치를 유지하고 없는 기능을 새로 만들지 않는다.

5. 기술 선택 원칙

- 현재 Flex/Grid와 콘텐츠별 줄바꿈 보완을 우선한다.
- 컨테이너 쿼리는 같은 컴포넌트를 서로 다른 폭에 재사용할 필요가 생길 때 검토한다.
- 전체 화면 고정 UI가 없어 svh/dvh를 즉시 도입할 근거는 부족하다.
- dvh가 화면 키보드 문제까지 자동으로 해결하지는 않는다.
- VisualViewport는 실제 필요성이 확인될 때만 사용한다.
  viewport 크기 변화만으로 키보드 열림을 판단하지 않는다.
- Device Posture는 접힘 상태, Viewport Segments는 분리된 화면 영역 정보다.
  제한적·실험적 지원 기능이므로 선택적으로 사용하고 기본 읽기·탐색은 API 없이 유지한다.
- 반응형 이미지와 이미지 크기 지정은 이미 일부 구현되어 있다.
  대표 이미지도 lazy loading이므로 실제 LCP 측정 후 로딩 우선순위를 결정한다.
- 별도 모바일 사이트, 기종 분기, 새 UI 라이브러리는 현재 문제 해결에 필요하지 않다.
- overflow-x:hidden으로 문제를 가리거나 글씨·필수 정보를 줄이는 방식은 사용하지 않는다.

6. 미검증 항목의 확인 절차

가. 화면 크기와 확대
- 홈과 긴 상세를 320·360·390·430·600·768·1024·1280 CSS px로 검사한다.
- 기본 글꼴에서 767·768·769px 전환점과 가로 방향·낮은 창을 추가한다.
- 글자만 200% 확대, 페이지 확대, 모바일 핀치 확대는 각각 검사한다.
- 줄 간격 1.5, 문단 간격 2em, 자간 .12em, 단어 간격 .16em 적용도 검사한다.
- 기대 결과: 정보·기능 손실 없음. 가로 스크롤은 필요한 표·코드 안에 한정.

나. 탐색 흐름
- 임시 기사 12개 이상에서 검색 → 정렬 → 2페이지 → 기사 → 뒤로가기를 검사한다.
- 빈 검색, 색인 로딩 실패, 검색 해제, 한글 조합 중 입력도 확인한다.
- 기대 결과: 정확한 안내, 검색 조건·페이지 보존, 자연스러운 읽기 위치.

다. 실기기
- Android Chrome과 iOS Safari에서 키보드·주소창 변화·가로 회전을 확인한다.
- 폴드·플립에서 검색 중과 기사 중간에 접기·펼치기·분할 화면을 실행한다.
- 커버 화면은 실제 웹 실행 가능 여부부터 확인한다.
- 노치와 시스템 영역에 조작 요소가 가려지지 않는지 확인한다.
- 필요한 정보: 대상 모델, OS·브라우저 버전, 주요 앱 내부 브라우저.

라. 접근성과 콘텐츠
- 키보드·TalkBack·VoiceOver로 초점, 상태 안내, 표·코드 조작을 확인한다.
- WCAG 2.2 AA의 터치 대상 24×24 CSS px 기준과 간격·인라인 등 예외를 구분한다.
- 주요 독립 버튼 44×44 이상은 별도의 프로젝트 권장 목표다.
- 긴 저자명·해시·경로·많은 태그·조밀한 PNG·큰 표가 있는 자료를 추가로 확보한다.
- 브라우저 에뮬레이션을 실기기·스크린 리더 검증으로 취급하지 않는다.
- 자동 검사만으로 WCAG 전체 준수를 선언하지 않는다.

마. 성능과 실제 배포
- 느린 연결에서 이미지·검색 비용과 레이아웃 이동을 측정한다.
- 로컬 Lighthouse와 실제 사용자 Core Web Vitals는 구분한다.
- 실제 Pages 주소와 주요 앱 내부 브라우저에서 상세 직접 진입·새로고침·검색·뒤로가기,
  콘솔 오류, CSS·JS·이미지·검색 색인 로딩을 확인한다.

7. 권장 구현 순서와 완료 조건

1) 다크 버튼 대비·빈 검색 안내 수정: 상태별 대비와 네 가지 결과 상태 검사 통과.
2) 좁은 폭·확대 문제 재현 후 CSS 보완: 정보 손실 없이 재배치.
3) 페이지 이동·뒤로가기 보완: 검색부터 기사 열람 후 복귀까지 흐름 유지.
4) 실제 기술 기사 검사: 표·이미지·긴 문자열을 읽고 조작할 수 있음.
5) 많은 기사로 성능 측정 후 최적화: 불필요한 작업 감소와 기능 검사 통과.
6) 실기기 특수 문제만 추가 대응: 기본 탐색을 유지하면서 재현된 가림·상태 유실 해결.
